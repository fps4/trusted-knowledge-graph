# 11. Identity is asserted, not federated — one person per session

Status: accepted · 2026-09-25 · M1

## Context

The design makes every decision as the person asking, never as the application.
In the programme that is the OAuth 2.0 on-behalf-of flow on Entra: the assistant
holds a token for the lawyer, and the resolver validates it against the tenant.
A laptop lab has no tenant.

## Decision

- Each persona has a key in `secrets/`, generated by `make init`. The persona's
  MCP container is started with **only its own key** and mints a short-lived
  HS256 assertion (`sub`, persona, 60 seconds) on every call. The resolver
  verifies it and looks the persona up in `config/people.yaml`.
- **Identity is fixed when the container starts.** No tool takes a persona or a
  principal as a parameter. A role the model can pass is not a boundary.
- **One persona per Claude session.** A single project `.mcp.json` listing every
  persona would give one session every persona's tools at once. Each persona has
  its own config, used with `claude --strict-mcp-config --mcp-config mcp/<persona>.json`.
- **The MCP container cannot reach the stores.** It joins `tkg_edge`, where the
  only other service is the resolver; the stores are on `tkg_internal`.
- A service identity (`percy-svc`) exists so that it can be refused: the firm's
  assistant calling as itself gets nothing.

## Consequences

- **This is the one place the lab is weaker than the design**, and the README
  says so in those words. Anyone who can read `secrets/` can be anyone.
- What is identical to the programme is the property that matters: the decision is
  made as a person, and the application has no identity that sees more.
